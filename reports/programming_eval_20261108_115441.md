## 任务C 概念问答

### 1) C++ 里的 RAII 是什么？为什么它重要？举一个不用 RAII 会出问题的例子。
**RAII（Resource Acquisition Is Initialization）**  
- **定义**：在 C++ 中，资源（如内存、文件句柄、锁、网络连接等）在对象构造时获得，在对象析构时释放。  
- **核心思想**：把资源的生命周期绑定到对象的作用域，利用对象的构造/析构保证资源一定被正确释放。  

**为什么重要？**  
1. **异常安全**：若在构造后抛异常，析构会自动执行，资源不会泄漏。  
2. **代码简洁**：不必手动 `delete`、`close`、`free`，减少错误。  
3. **可读性**：资源管理与业务逻辑分离，代码更易维护。  

**不使用 RAII 的典型错误**  

```cpp
void foo() {
    FILE* f = fopen("data.txt", "r");   // 手动获取资源
    if (!f) return;

    // 读取文件
    char buf[256];
    fread(buf, 1, 256, f);

    // 这里出现异常或提前返回
    if (some_error) {
        return;          // 直接返回，f 仍未关闭
    }

    fclose(f);          // 只有正常路径才执行
}
```

- **问题**：若 `some_error` 为真，函数提前返回，`fclose` 从未执行，导致文件句柄泄漏。  
- **RAII 解决**：使用 `std::unique_ptr<FILE, decltype(&fclose)>` 或 `std::ifstream`，构造时打开，析构时自动关闭，异常路径也安全。  

> 通过 RAII，资源的获取与释放被绑定到对象的生命周期，保证无论何种退出方式（正常、异常、提前返回）都能正确释放。

### 2) Python 里「可变默认参数」有什么坑？为什么会发生？正确的写法是什么？
**可变默认参数**（mutable default arguments）是 Python 函数定义时把可变对象（如 `list`、`dict`、`set` 等）直接写成默认值。  
这会导致 **所有调用共享同一个对象**，从而产生意外的副作用。  

---

### 1. 发生原因

```python
def append_to_list(item, lst=[]):
    lst.append(item)
    return lst
```

- `lst=[]` 在函数定义时就创建了一个列表对象。  
- 每次调用 `append_to_list(1)` 时，`lst` 不是新建，而是 **引用同一个列表**。  
- 结果：  
  ```python
  >>> append_to_list(1)
  [1]
  >>> append_to_list(2)
  [1, 2]          # 之前的 1 仍在
  ```

这与“可变对象会被修改”本身无关，而是因为**默认值在函数体外一次性创建**，而不是每次调用时重新创建。

---

### 2. 正确写法

最常见的做法是使用 **不可变对象**（如 `None`）作为默认值，然后在函数内部判断并创建：

```python
def append_to_list(item, lst=None):
    if lst is None:
        lst = []          # 每次调用都新建
    lst.append(item)
    return lst
```

- 也可以直接用 `*args`、`**kwargs` 或者 `list()` 之类在函数体内创建。  
- 只要保证 **每次调用都得到一个新的可变对象**，就不会出现共享副作用。

---

### 3. 典型坑点

| 现象 | 说明 |
|------|------|
| 之前的调用残留 | 之前的 `append_to_list(1)` 结果会在后续调用中出现 |
| 传入可变对象后被修改 | `def f(a, b=[]): b.append(a)` 传入外部列表 `x` 时 `x` 也会被改 |
| 递归调用共享 | `def f(n, acc=[]): if n==0: return acc; acc.append(n); return f(n-1, acc)` 递归时 `acc` 共享导致错误 |

---

### 4. 结论

- **不要把可变对象直接写成默认值**。  
- 用 `None`（或不可变对象）做占位，函数内部再创建。  
- 这样既能避免共享副作用，又能保持默认值的“缺省”语义。

### 3) 进程和线程的区别是什么？什么场景适合用多进程、什么场景适合用多线程？
进程（Process）与线程（Thread）是操作系统调度的两种粒度，主要区别如下：

| 维度 | 进程 | 线程 |
|------|------|------|
| **内存空间** | 独立地址空间，互不共享；需要显式 IPC（管道、共享内存、消息队列等） | 同一进程内共享代码、数据、堆、全局部；仅栈和寄存器独立 |
| **调度单元** | 进程级调度，系统开销大 | 线程级调度，开销小 |
| **创建/销毁** | 需要系统调用（fork/exec 等），耗时较长 | 轻量级，创建销毁快 |
| **错误隔离** | 一个进程崩溃不影响其他进程 | 一个线程崩溃可能导致整个进程崩溃 |
| **通信成本** | 高（IPC 需要拷贝/同步） | 低（共享内存） |
| **安全性** | 高（隔离） | 低（共享导致竞争） |
| **上下文切换** | 频繁切换时需要保存/恢复完整寄存器、内存映射 | 只需切换栈、寄存器，速度快 |

---

### 何时用多进程

| 场景 | 原因 |
|------|------|
| **安全隔离** | 需要把不可信或可能崩溃的代码放在独立进程，防止影响主程序 |
| **多核利用** | 进程间天然并行，适合 CPU 密集任务 |
| **资源隔离** | 进程拥有独立文件句柄、网络连接等，避免共享导致冲突 |
| **跨语言/平台** | 进程可直接调用不同语言编译的可执行文件 |
| **内存限制** | 进程可通过 `ulimit` 控制单个进程的内存使用 |

**典型例子**：Web 服务器的 worker 进程、数据库的查询进程、视频转码工具、容器化部署。

---

### 何时用多线程

| 场景 | 原因 |
|------|------|
| **共享数据** | 线程共享同一对象，避免拷贝成本 |
| **I/O 等待** | 线程可在等待 I/O 时让 CPU 处理其他线程，提升吞吐量 |
| **轻量级并发** | 线程创建销毁快，适合短生命周期任务 |
| **内存受限** | 线程共享堆，内存占用低 |
| **细粒度同步** | 线程间可用锁、条件变量、事件等细粒度同步机制 |

**典型例子**：GUI 主线程 + 后台 I/O 线程、网络客户端的接收/发送线程、游戏引擎的渲染/物理线程。

---

### 选择建议

1. **安全性优先** → 多进程。  
2. **共享大量数据** → 多线程。  
3. **任务短小、频繁** → 多线程。  
4. **任务长大、CPU 密集** → 多进程。  
5. **跨语言或需要独立资源** → 多进程。  

> 综上，进程与线程各有优势，实际项目中常见“进程+线程”混合模式：主进程负责调度，内部用线程处理并发任务。
